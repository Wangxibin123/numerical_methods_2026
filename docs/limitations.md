# 局限 / Limitations

写到正文也写到这里，避免读者把项目当成 “生产可上线” 的调度系统。

## 数据层面

1. **dropoff 流不是真实空车库存。**
  $Q_{i,t}$ 是当前小时区域 $i$ 内 \emph{乘客下车次数}。我们用它代理
   “短时间内潜在可服务的车辆”。这与平台实时定位到的真实空车数据存在偏差：
  - 部分车辆下车后立刻被同区域已等候的乘客上车（再分配延迟极短）；
  - 司机可能下车后跨区移动数公里再等单；
  - 收车 / 用餐 / 加油等导致的暂时不可用没有体现。
2. **没有天气、道路、活动数据。** 雨雪 / 道路施工 / 体育赛事会显著扭曲
  pickup 分布，我们的预测器完全看不到。
3. **公开数据约两个月延迟。** 默认使用 2024 Q1，无法对实时调度做评估。

## 模型层面

1. **LP 是连续 relaxation。** $x_{ij}$ 不是整数车辆数，
  解释为 “期望调度强度”。实际部署需要四舍五入 + 二次分配。
2. **成本矩阵忽略实时路况。** $c_{ij}$ 来自训练期 OD 行程的 tripdistance
  中位数；不同时段的实际行驶时间差异未被建模。
3. **lambda 是策略参数，不是估计参数。** 我们用敏感性分析报告了
  不同 $\lambda$ 下的 cost-service tradeoff，没有给出 “最优 $\lambda$”。
4. **评估假设调度瞬时执行。** 真实世界中调度指令到车辆移动需要若干分钟，
  未满足需求可能高于我们的报告值。

## 实验层面

1. **测试小时数量有限。** 默认 24 小时（一日循环），结论在更广窗口下需要
  重新评估（季节性、节假日等）。
2. **Monte Carlo 默认 Poisson。** 这是对需求波动的简化；
  `cfg.mc_distribution = 'bootstrap'` 可启用残差 bootstrap，更接近真实分布。
3. **未做端到端的 cost / quality 校准。** 例如 “miles per unmet trip” 的转换
  是固定 $\lambda$，没有结合票价收入。
